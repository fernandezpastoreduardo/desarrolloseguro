# Plan de pruebas

## Estado y ejecución

La suite cubre reglas del core, persistencia, API de estado/informe, políticas de ingesta, Compose y configuración TLS. CI ejecuta lint, typecheck, tests, build, integración PostgreSQL efímera, políticas estáticas y un smoke aislado de la imagen.

La suite PostgreSQL puede crear/borrar bases y roles globales. En local requiere `DS_TEST_POSTGRES_ISOLATED=1`, URL de loopback sin query/fragmento y base administrativa con prefijo `development_security_test_`. Ejecutarla solo contra un cluster local dedicado. CI usa un servicio PostgreSQL/pgvector efímero.

Las pruebas de políticas TLS generan certificados sintéticos temporales. No demuestran configuración de certificados reales, conectividad de producción, reglas del host, egress, carga ni restauración de backups. El modelo de amenazas y la evidencia exigida para scans están en [scanner-safety.md](scanner-safety.md); las pruebas locales del transporte no sustituyen las pruebas de aislamiento del runtime real.

## Cobertura a mantener

| Área | Comprobaciones |
| --- | --- |
| Core | Validación de hostname, perfil/scope, normalización y reglas de veredicto. |
| API | Validación de entrada, respuestas de estado/informe y solicitud autorizada, rate limiting y errores públicos seguros. |
| Persistencia | Migraciones, constraints, leases, concurrencia entre dominios, cuotas atómicas (10 en cola, 1 en ejecución, 24 h por dominio, 1000 altas on-demand), reintentos, proyección pública y mínimos privilegios. |
| Docker | Servicios, redes internas, loopback-only para web, secretos y volumen exclusivos del proyecto. |
| TLS | Validación de nombres/CA y configuración de proxy con material sintético. |
| UI | Flujos accesibles, estados de carga/error, navegación y adaptación móvil. |
| Navegador real | Playwright con Chromium arranca Vite localmente y comprueba el portal, cambio de tema, búsqueda de un dominio y solicitud autorizada encolada mediante API simulada; no realiza solicitudes a terceros. Ejecutar con `pnpm test:e2e`; CI instala Chromium y corre estas pruebas. No sustituye pruebas de API, accesibilidad completa ni recorrido con backend real. |
| Primitivas, observador y executor local | Validación DNS/IP, lookup fijado al hostname exacto del trabajo, pinning TLS, límite de respuesta, HTTP→HTTPS de mismo host/puerto/ruta con servidores sintéticos loopback, señales derivadas, métricas de intentos/bytes recibidos y clasificación segura de errores TLS. Un DNS que cambia de IP pública a loopback se rechaza antes de la segunda conexión; no valida firewall ni egress del host. |
| Ensamblador fixture-only | Cobertura exacta de `transport-v1`, errores categóricos sin filtrar detalles y derivación del veredicto; no valida adaptadores de red ni produce tráfico. |
| Canal de proceso y PostgreSQL | El hijo recibe solo hostname/perfil en un protocolo acotado, con entorno vacío y sin lease; el coordinador valida y persiste el resultado. La suite `pnpm test:postgres` recorre el canal con fixture hasta el informe público en una base opt-in aislada. El canal no prueba sandbox del sistema operativo. |
| Fallos y reintentos | El executor no filtra su excepción; la DB solo libera el trabajo con un lease vigente, aplica un máximo de intentos y backoff, y publica únicamente códigos categóricos permitidos. |
| Sandbox Linux del executor | CI ejecuta `pnpm sandbox:check`: construye imagen separada y confirma usuario, capacidades, no-new-privileges, filesystem read-only, tmpfs, ausencia de Docker socket/secretos/interfaces/rutas por defecto de red y topes efectivos de cgroup v2; corre sin red y sin montajes del host. También valida el entrypoint real con input rechazado antes de la red. No demuestra política de egress ni aislamiento del VPS. |
| Política de destino para egress | Pruebas unitarias permiten solo el hostname exacto del trabajo en puertos 80/443 y devuelven IP públicas A/AAAA validadas para conexión fijada. Se rechazan hostname ajeno, puertos alternativos, respuestas mixtas y rebinding. No abre sockets ni demuestra aislamiento de red. |
| Aplicación de autorización al lookup de socket | `createEgressAuthorizedLookup` invoca la autorización con el puerto fijo del transporte, filtra por familia solicitada y entrega las IP públicas validadas sin una nueva resolución. El transporte HTTP usa 80 y HTTPS 443; las pruebas usan resolvers sintéticos. Esta política de aplicación no reemplaza firewall ni valida tráfico al gateway/host. |
| Broker IPC de sondas por perfil | Pruebas unitarias y de socket Unix temporal permiten únicamente DNS, TLS, HEAD, GET y cabeceras del hostname del trabajo, cada operación una vez, con máximo dos operaciones en paralelo y cuotas agregadas de solicitudes/bytes. Comprueban tamaño del protocolo, correlación, directorio privado del socket, permisos `0660` y rechazo de hostname ajeno. Hay targets Docker separados y el entrypoint valida el scope del trabajo antes de escuchar. La prueba Docker conecta broker y executor en contenedores sin red mediante un volumen privado; el executor usa el volumen como solo lectura y falla cerrado sin socket. El runner implementa el ciclo de vida efímero por trabajo y el smoke elimina contenedores/volumen; no se demuestra firewall ni egress efectivo. |
| Worker arrancable | Pruebas verifican configuración obligatoria por fichero secreto, rol/base `ds_worker`/`desarrollo_seguro`, identidad Unix explícita, rechazos de rutas relativas/valores malformados, polling serial, espera al estar idle, backoff ante errores y parada del bucle con `AbortSignal`; el entrypoint traduce SIGTERM/SIGINT a esa señal. El procesador recupera leases vencidos antes del claim, cada 15 segundos como máximo, falla cerrado ante error y comparte recuperación concurrente. La composición conecta telemetría filtrada, store y cliente del supervisor; no se añade a Compose ni se prueba contra una cola de producción. |
| Scheduler de retención | Pruebas verifican corte fijo de 90 días, ejecución al arranque y luego cada 24 horas, serialización, continuación tras fallo con categoría no sensible, parada por `AbortSignal`, URL `ds_retention` desde secreto y TLS con CA verificada en producción. PostgreSQL aislado comprueba que el rol solo ejecuta el purgado; el proceso permanece fuera de Compose hasta validar batch/impacto y backup/restauración. |
| Telemetría del procesador | Las pruebas verifican una categoría fija de resultado y duración no negativa; el evento no acepta hostname, ID de trabajo, lease, perfil ni texto de error. Un fallo del sink no cambia el resultado del trabajo. El adaptador JSON Lines conserva solo outcome/duración, rechaza valores inválidos y escribe a `stdout`; queda conectado al entrypoint no desplegado. |
| Cliente y servidor del supervisor de runtime | Pruebas con socket Unix local verifican protocolo correlacionado, hostname normalizado/perfil, rechazo de propietario/grupo no esperados, directorio modificable, campos extra, respuesta inválida, cancelación al desconectar y máximo de un trabajo activo. Pruebas del runner verifican respuesta correlacionada, categorías seguras y limpieza incluso ante fallos; `pnpm sandbox:check` ejecuta el runner Docker real en Linux, confirma los cinco checks `unknown` bajo `network none` y limpia contenedores/volumen. El cliente está conectado al entrypoint worker no desplegado; no hay prueba de egress con conectividad habilitada. |
| Executor y runtime futuro | Separación de credenciales, bloqueo real de destinos privados/host/IPv6, DNS rebinding, límites globales y ausencia de tráfico a servicios señuelo en el runtime de despliegue. La prueba `network none` no cubre egress permitido ni firewall del host. |

## Límites

El executor de red compuesto tiene un entrypoint worker local y existe un scheduler de retención, pero ninguno se incluye en el despliegue. La interfaz permite solicitar una admisión mediante API; CI no ejecuta esos análisis ni accede a sistemas externos. Las pruebas de UI simulan la respuesta de admisión y verifican que no hay solicitudes de terceros; las pruebas PostgreSQL verifican cuotas y el alta transaccional. El flujo fixture del worker comprueba persistencia sin egress. Antes de habilitar scans reales será necesario demostrar firewall/egress efectivo, bloqueo de destinos privados, sandbox del proceso, límites de recursos y privacidad en el runtime elegido.
