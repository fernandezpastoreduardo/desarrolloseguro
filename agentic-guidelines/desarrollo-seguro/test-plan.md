# Plan de pruebas

## Estado y ejecución

La suite cubre reglas del core, persistencia, API de estado/informe, políticas de ingesta, Compose y configuración TLS. CI ejecuta lint, typecheck, tests, build, integración PostgreSQL efímera, políticas estáticas y un smoke aislado de la imagen. El job de despliegue verifica después que `.com` redirige a `.org` sin exponer `:8080` y solicita un informe real nuevo de `grumphya.com`; exige `domain-v3`, nueve controles, al menos cinco comprobaciones concluyentes, medición de todas las versiones TLS, cookies/rastreadores/rendimiento inicial y puntuación consistente. La sonda manual `audit:egress:probe` clasifica DNS, TCP, TLS y HTTP sin guardar cuerpos ni credenciales.

Una prueba de implementación o de CI no demuestra por sí sola operación en
producción ni aceptación de una etapa. Para aceptar C se necesita, además,
evidencia del scheduler horario real, actualización de certificación/sello,
recuperación ante fallo y notificación autorizada. La recuperación de leases ya
tiene evidencia en producción; queda pendiente observar una incidencia que
active la notificación. La auditoría privada de D y
la puntuación global absoluta se validan por separado.

La suite PostgreSQL puede crear/borrar bases y roles globales. En local requiere `DS_TEST_POSTGRES_ISOLATED=1`, URL de loopback sin query/fragmento y base administrativa con prefijo `development_security_test_`. Ejecutarla solo contra un cluster local dedicado. La puerta `pnpm ci:verify postgres` valida esas condiciones antes de ejecutar Vitest para que una configuración ausente no convierta los tests en omitidos silenciosos. CI usa un servicio PostgreSQL/pgvector efímero.

Las pruebas de políticas TLS generan certificados sintéticos temporales. No demuestran configuración de certificados reales, conectividad de producción, reglas del host, egress, carga ni restauración de backups. El modelo de amenazas y la evidencia exigida para scans están en [scanner-safety.md](scanner-safety.md); las pruebas locales del transporte no sustituyen las pruebas de aislamiento del runtime real.

## Cobertura a mantener

| Área | Comprobaciones |
| --- | --- |
| Core | Validación de hostname, perfil/scope, normalización y reglas de veredicto. |
| API | Validación de entrada, respuestas de estado/informe y solicitud autorizada, rate limiting y errores públicos seguros. |
| Persistencia | Migraciones, constraints, leases, concurrencia entre dominios, cuotas atómicas (10 en cola, 1 en ejecución, caché de 60 min y ventana de 24 h reactivadas por la migración beta 025, 1000 altas on-demand), reintentos tras fallos (027), protección contra informes de certificación fuera de orden (028), proyección pública y mínimos privilegios. PostgreSQL verifica las 31 migraciones, la respuesta cacheada, el bloqueo de una nueva admisión dentro de la ventana y la invariancia del historial. |
| Scoring ético | La rúbrica evalúa solo controles con evidencia validada y deja criterios no observados en `unknown`. `domain-v3` añade a `domain-v2` la matriz de versiones TLS, además de cookies iniciales, referencias de rastreadores conocidos en el HTML y latencia/tamaño de una respuesta GET; no afirma consentimiento, conexión efectiva, ventas de datos ni Core Web Vitals. La cobertura y las razones acompañan cada puntuación. El smoke acepta un criterio TLS `unknown` solo si cada versión aporta un booleano de aceptación o un código de sonda allowlisted. |
| Auditoría interna D | El contrato de D-01 acepta solo `grumphya.com` en producción, scopes allowlisted y retención máxima de 30 días. El adaptador autoriza solo `GET` a recursos y rutas allowlisted, sin query, fragmentos ni saltos de directorio; el lector fija el origen HTTPS, no envía credenciales y valida el JSON con el parser del recurso. D-02 valida snapshots con digest, exposición, privilegios y transporte TLS, rechaza comandos, rutas, variables y datos de base, y solo proyecta `infrastructure.tls` con transporte verificado. D-03 valida digests del artefacto/dependencias y un inventario agregado de contadores de riesgo, sin SBOM ni nombres de paquetes; solo proyecta checks explícitos de dependencias, secretos fuera de la imagen y superficie API allowlisted. D-04 valida flujos sintéticos y referencias hash, y rechaza credenciales, tokens, correos e IDs reales. D-05 valida métricas allowlisted de E2E, rendimiento, accesibilidad y responsive con límites numéricos, y rechaza HTML, capturas, trazas y URLs. D-06 valida señales agregadas de almacenamiento, terceros, consentimiento, transparencia y minimización; rechaza nombres de cookies, dominios, textos, scripts y afirmaciones de venta de datos. D-07 proyecta cada observación a un único criterio, rechaza duplicados antes de puntuar y mantiene la puntuación externa separada. D-08 coordina recursos de forma secuencial con `internal-audit-runner`; propaga cancelación segura, devuelve categorías de fallo sin exponer mensajes del runtime, comprueba scopes finos de ética/IA, rechaza evidencias futuras y no fabrica un informe ante evidencia inválida o no disponible. El evaluador interno mantiene `externalScore` en `null`, no calcula score con evidencia incompleta, distingue `unknown`/`not_applicable` y bloquea fallos críticos. No usa fixtures como evidencia de producción ni abre conexiones por sí mismo. |
| Docker | Servicios, redes internas, loopback-only para web, secretos y volumen exclusivos del proyecto. La imagen del coordinador contiene el CLI Alpine; CI lo ejecuta sin daemon para detectar binarios incompatibles antes del deploy. |
| TLS | Validación de nombres/CA y configuración de proxy con material sintético. |
| UI | Flujos accesibles, estados de carga/error, navegación y adaptación móvil. |
| Historial público | API acotada a doce informes externos, exclusión de dominios opt-out, orden temporal, UUIDs y enlaces de ficha; la UI comunica la comparabilidad por perfil y no muestra evidencias internas. |
| Hostnames de Grumphya y sellos | Pruebas unitarias verifican que el transporte sigue únicamente el par autorizado, 301/308 eligen el destino observado, códigos temporales no canonizan, bucles y destinos ajenos fallan cerrados, la ingesta conserva campos acotados y PostgreSQL resuelve el alias solo con un informe reciente. La integración comprueba que el alias presenta el informe certificado del destino y oculta la certificación del informe de origen; el mismo token debe seguir al nuevo `certifiedReportId` tras una renovación elegible, pero falla al suspenderse, caducar el informe o token, revocarse o perderse la evidencia de redirección. El widget obtiene el ID actual por `GET /domains/:hostname/status`, ignora un ID estático antiguo, oculta totalmente el enlace al fallar y no expone el token. |
| Navegador real | Playwright con Chromium arranca Vite localmente y comprueba el portal, cambio de tema, búsqueda, solicitud autorizada y actualización automática hasta que aparece un informe nuevo mediante API simulada; no realiza solicitudes a terceros. La barra de progreso es indeterminada y refleja únicamente los estados reales `queued`, `running` o `updating`; no atribuye porcentajes sin progreso medido por el servidor. El sondeo se limita a 180 consultas cada cinco segundos (15 minutos) mientras haya trabajo activo y se detiene tras la primera respuesta que no muestra ni trabajo activo ni informe nuevo; ese desacuerdo debe permitir reintentar y nunca presentarse como informe generado. Ejecutar con `pnpm test:e2e`; CI instala Chromium y corre estas pruebas. No sustituye pruebas de API, accesibilidad completa ni recorrido con backend real. |
| Primitivas, observador y executor local | Validación DNS/IP, lookup fijado al hostname exacto del trabajo, pinning TLS, límite de respuesta, HTTP→HTTPS de mismo host/puerto/ruta con servidores sintéticos loopback, señales derivadas, métricas de intentos/bytes recibidos y clasificación segura de errores TLS/DNS/transporte. El executor de red rechaza completar un trabajo cuando todas las sondas devuelven evidencia vacía. Un DNS que cambia de IP pública a loopback se rechaza antes de la segunda conexión; no valida firewall ni egress del host. |
| IPC del broker | Executor `transport-v1` completo contra broker Unix con cinco checks permitidos, dos observaciones simultáneas y conexiones que cierran asincrónicamente; no permite encolar pruebas fuera del contrato. |
| Ensamblador fixture-only | Cobertura exacta de `transport-v1`, errores categóricos sin filtrar detalles y derivación del veredicto; no valida adaptadores de red ni produce tráfico. |
| Canal de proceso y PostgreSQL | El hijo recibe solo hostname/perfil en un protocolo acotado, con entorno vacío y sin lease; el coordinador valida y persiste el resultado. La suite `pnpm test:postgres` recorre el canal con fixture hasta el informe público en una base opt-in aislada. El canal no prueba sandbox del sistema operativo. |
| Fallos y reintentos | El executor no filtra su excepción; la DB solo libera el trabajo con un lease vigente, aplica un máximo de intentos y backoff, y publica únicamente códigos categóricos permitidos. |
| Sandbox Linux del executor | CI ejecuta `pnpm sandbox:check`: construye imagen separada y confirma usuario, capacidades, no-new-privileges, filesystem read-only, tmpfs, ausencia de Docker socket/secretos/interfaces/rutas por defecto de red y topes efectivos de cgroup v2; corre sin red y sin montajes del host. También valida el entrypoint real con input rechazado antes de la red. No demuestra política de egress ni aislamiento del VPS. |
| Política de destino para egress | Pruebas unitarias permiten solo el hostname exacto del trabajo en puertos 80/443 y devuelven IP públicas A/AAAA validadas para conexión fijada. Se rechazan hostname ajeno, puertos alternativos, respuestas mixtas y rebinding. No abre sockets ni demuestra aislamiento de red. |
| Aplicación de autorización al lookup de socket | `createEgressAuthorizedLookup` invoca la autorización con el puerto fijo del transporte, filtra por familia solicitada y entrega las IP públicas validadas sin una nueva resolución. El transporte HTTP usa 80 y HTTPS 443; las pruebas usan resolvers sintéticos. Esta política de aplicación no reemplaza firewall ni valida tráfico al gateway/host. |
| Broker IPC de sondas por perfil | Pruebas unitarias y de socket Unix temporal permiten únicamente DNS, TLS, HEAD, GET y cabeceras del hostname del trabajo, cada operación una vez, con máximo dos operaciones en paralelo y cuotas agregadas de solicitudes/bytes. Comprueban tamaño del protocolo, correlación, directorio privado del socket, permisos `0660` y rechazo de hostname ajeno. Hay targets Docker separados y el entrypoint valida el scope del trabajo antes de escuchar. La prueba Docker conecta broker y executor en contenedores sin red mediante un volumen privado; el executor usa el volumen como solo lectura y falla cerrado sin socket. El runner implementa el ciclo de vida efímero por trabajo y el smoke elimina contenedores/volumen; no se demuestra firewall ni egress efectivo. |
| Worker arrancable | Pruebas verifican configuración obligatoria por fichero secreto, rol/base `ds_worker`/`desarrollo_seguro`, identidad Unix explícita, rechazos de rutas relativas/valores malformados, polling serial, espera idle, backoff y parada por señal. El procesador recupera leases vencidos antes del claim, como máximo cada 15 segundos, y falla cerrado ante error. La composición conecta telemetría filtrada, store y cliente del supervisor. Compose incluye el servicio worker limitado al backend interno y al socket Unix de runtime. |
| Scheduler de retención y certificación | Pruebas verifican corte fijo de 90 días, limpieza pública `on_demand` a 30 días sin certificación activa, conservación de dominios monitorizados e informes certificados, auditorías vencidas cada hora, prioridad de solicitudes manuales, ejecución al arranque y luego en intervalos fijos, serialización, continuación tras fallo con categoría no sensible, parada por `AbortSignal`, URL `ds_retention` desde secreto y TLS con CA verificada en producción. PostgreSQL aislado comprueba que el rol solo ejecuta las funciones protegidas; Compose mantiene ambos procesos en la red interna, sin puertos ni egress, y sus fallos se emiten mediante JSONL allowlisted sin datos sensibles. Los ciclos completados añaden únicamente un contador agregado acotado (`affectedCount`) para distinguir cero trabajo de trabajo encolado o purgado. La ejecución horaria real, el impacto y la recuperación del VPS siguen siendo validaciones operativas. |
| Telemetría del procesador | Las pruebas verifican una categoría fija de resultado y duración no negativa, además de categorías allowlisted para errores de procesamiento. Los eventos no aceptan hostname, ID de trabajo, lease, perfil ni texto de error. Un fallo del sink no cambia el resultado del trabajo. El adaptador JSON Lines conserva solo outcome o code y duración, rechaza valores inválidos y escribe a `stdout`; queda conectado al entrypoint no desplegado. |
| Cliente y servidor del supervisor de runtime | Pruebas con socket Unix local verifican protocolo correlacionado, hostname/perfil normalizado, propietario/grupo esperados, directorio privado, payloads, respuesta, cancelación y concurrencia. Las pruebas de configuración/entrypoint comprueban rutas, imágenes y composición con el runner Docker y socket local fijado. El runner verifica respuestas, errores seguros y limpieza idempotente: si un contenedor o volumen ya no existe, se considera retirado; los errores transitorios de borrado se reintentan tres veces con un límite de tres segundos por operación; cualquier otro error persistente falla cerrado. Los diagnósticos JSON Lines del coordinador indican fase, código categórico, causa Docker clasificada y, en limpieza, intento; si las sondas no generan evidencia, pueden añadir hasta cinco pares allowlisted operación/código. El protocolo y el sink rechazan operaciones duplicadas y texto arbitrario; nunca registran hostname, identificadores, rutas privadas, cabeceras ni stderr crudo de Docker. `pnpm sandbox:check` ejecuta el runtime Docker real en Linux con executor `network none`. El preflight valida que solo el broker obtiene red y que la política de host se limita a `br-ds-egress`; queda pendiente validar en VPS los destinos señuelo y ejecutar un informe real desde el frontend. |
| Executor y runtime futuro | Separación de credenciales, bloqueo real de destinos privados/host/IPv6, DNS rebinding, límites globales y ausencia de tráfico a servicios señuelo en el runtime de despliegue. La prueba `network none` no cubre egress permitido ni firewall del host. |

## Límites

CI no ejecuta análisis ni accede a sistemas externos. Las pruebas de UI simulan la admisión y verifican que no hay solicitudes de terceros; PostgreSQL verifica cuotas y alta transaccional. El flujo fixture comprueba persistencia sin egress. Antes de aceptar scans reales en producción se debe validar el firewall con servicios señuelo y revisar un informe producido por el runtime.
